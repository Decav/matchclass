## 1. Contexto y Problema

La raíz `/` sigue sirviendo `PaHealth`, la pantalla de diagnóstico de Firebase que RC-001 puso ahí como andamio de arranque: hoy, cualquiera que entre a MatchClass sin un enlace directo aterriza en una lista de servicios y puertos de emulador. No hay ninguna pantalla que explique qué es el producto, y un alumno con un código en la mano no tiene dónde escribirlo salvo que alguien le pase la URL exacta de `/acceso`.

## 2. Objetivo

Reemplazar `/` por la landing pública: hero con el nombre y el tagline, un campo para entrar directo con el código de sala, tres cards que explican el flujo, y un acceso para ayudantes. Sin autenticación, y con redirección al dashboard si ya hay sesión.

---

## 3. Entidades y Value Objects

No se agregan entidades. La validación del código reusa `Room` y `RoomRepository.findByCode` (RC-003), y el largo de 6 caracteres ya está en `roomCodeSchema` (`src/modules/access/core/schemas/room-code.schema.ts`) — **que no se importa desde acá**: los módulos no se importan entre sí, así que la landing define su propio schema de un campo (ver §10).

## 4. Errores de Dominio

| Error | Origen | Manejo | Escenario |
|-------|--------|--------|-----------|
| `RoomNotFoundError` | `RoomRepository.findByCode` devuelve `null` | Borde rojo en el input + "Código inválido. Revisa con tu ayudante" — el mismo texto que ya muestra `Q4RoomCodeForm` (RC-003) para el mismo caso | 3 |
| (validación local) | menos de 6 caracteres | El botón "Entrar" queda deshabilitado; no se consulta Firestore | — |
| (sin tipo propio) | falla de red al validar | Mismo mensaje de código inválido: para el visitante la acción falló igual, y la landing no es lugar para un estado de error dedicado que ningún escenario pide | — |

**Sala cerrada (D4 aprobada).** Si el código existe pero `status !== 'active'`, la landing **no** lo trata como error: navega igual a `/acceso?tipo=alumno&codigo=…` y es el flujo del alumno el que muestra "Esta sala ya no acepta respuestas" (RC-003, ya implementado). La landing solo verifica que la sala exista — la regla de "sala cerrada" vive en un único lugar.

## 5. Puertos (Interfaces)

- **RoomRepository** — sin cambios: `findByCode(code)` (RC-003) ya resuelve la validación

- **useAuthStore** — sin cambios: la landing lee `status` para el Escenario 5

- **`src/modules/home/core/schemas/landing-code.schema.ts`** (nuevo): `z.object({ code: z.string().length(6, ...) })`. Duplica el `roomCodeSchema` de `access` a propósito — un schema de una línea es más barato que promover a `resources/` un VO que las dos pantallas podrían divergir mañana (`access` valida celda por celda, la landing un campo suelto)

- **`src/modules/home/core/hooks/use-landing-code-mutation.ts`** (nuevo): valida el código y navega a `/acceso?tipo=alumno&codigo=XXX`. No reusa `useValidateRoomCodeMutation` (módulo `access`) ni crea la sesión anónima: eso lo sigue haciendo el flujo de `/acceso` al montar

- **Componentes nuevos** (`src/modules/home/components/`):
  - `q4-landing-code-form/` — barra de código + botón "Entrar" + error inline
  - `q2-landing-feature-card/` — una de las tres cards (ícono, título, descripción)
  - `pa-landing/` — página: hero, cards, footer, y el guard del Escenario 5

- **Rutas** (D1/D2 aprobadas):
  - `@modules/home` exporta `homePublicRoutes` (solo `/`, registrada fuera de `Q5ProtectedRoute`) además de `homeRoutes`, que sigue completo dentro del guard
  - `healthRoutes` pasa de `/` a `/health`. `PaHealth` **no se elimina**: sigue siendo la forma rápida de verificar que los emuladores responden

## 6. Use Cases

| Use Case | Input | Output | Errores posibles |
|----------|-------|--------|-------------------|
| RedirectAuthenticatedVisitor | `AuthStatus` del store | redirect a `/dashboard` o render de la landing | — |
| SubmitLandingCode | code (6 chars) | navegación a `/acceso?tipo=alumno&codigo=XXX` | `RoomNotFoundError` |

### RedirectAuthenticatedVisitor
1. `status === Authenticated` → `<Navigate to="/dashboard" replace />` (Escenario 5)
2. `status === Idle | Loading` → spinner: **no se redirige mientras la sesión se restaura**, que es el mismo error que `Q5ProtectedRoute` evita con sus tres estados
3. `status === Unauthenticated` → se renderiza la landing

### SubmitLandingCode
1. Con menos de 6 caracteres, "Entrar" está deshabilitado (sin lectura a Firestore)
2. Con 6, `RoomRepository.findByCode(code)`; el botón queda en `loading`
3. Si no existe → error inline y **no** se navega (Escenario 3)
4. Si existe → `navigate('/acceso?tipo=alumno&codigo=XXX')`, donde `Q5StudentAccessFlow` precarga el código y sigue el flujo de HU-01 (Escenario 2). Vale también para una sala cerrada: la landing no mira el `status` (D4)

## 7. Contrato (Firebase)

| Operación | Método Firestore | Input | Output | Errores |
|-----------|-------------------|-------|--------|---------|
| Validar código | `getDocs(query(collection(db,'rooms'), where('code','==',CODE), limit(1)))` | code (6 chars) | `Room \| null` | `unavailable` |

Sin escrituras. `firestore.rules` ya permite `allow read: if true` en `rooms` — la lectura pública del código es una decisión asumida desde RC-003 ("quien adivine un código ve el nombre de la sala"), no algo que introduzca este RC.

## 10. Notas

**Medidas leídas del frame `Landing Page` (`YbL8k`).** Página de 1000px sobre `--mc-surface`, en columna. *Hero*: padding `80/40/60/40`, gap 32, centrado; logo 72×72 radio 18 con "MC" en 28px/700; título 42px/700; tagline 18px normal. *Barra de código*: 460×56, radio 14, borde `--mc-border`, padding 4 — input de 48px con placeholder "Ingresa el código de tu sala" (15px) y botón de 44px radio 10, navy, label "Entrar" (14px/600). *Divisores*: 600×1. *Cómo funciona*: título 28px/700, gap 32, tres cards `fill_container` de radio 16 con borde, padding 28 y gap 16; ícono en cuadro 56×56 radio 14 con el color al 10% de fondo. *Footer*: padding 40, gap 8.

| Card | Ícono Lucide | Fondo/color del ícono | Título | Descripción |
|---|---|---|---|---|
| 1 | `calendar-plus` | `--mc-brand-secondary` (indigo) al 10% | Crea una sala | El ayudante crea la sala en segundos y recibe un código único para compartir |
| 2 | `link` | `--mc-brand-accent` (dorado) al 10% | Comparte el código | Los alumnos ingresan sin registro ni contraseña. Solo necesitan el código de 6 caracteres |
| 3 | `trending-up` | `--mc-heatmap-high` (verde) al 10% | Descubre el mejor horario | Heatmap de colores y ranking top 3 con los bloques de mayor disponibilidad |

**Dos desviaciones del material de origen, ya resueltas:**
- El footer de la HU decía "¿**Sos** ayudante?" (voseo), contra el "¿**Eres** ayudante?" del nodo del `.pen` y el español neutro de `docs/estandar-idioma.md`. Diego corrigió la HU el 2026-08-09; las dos fuentes ya coinciden.
- El título "Cómo funciona" viene con `fontFamily: "Funnel Sans"` en el nodo. El design system fija Inter como inviolable para todo el texto de UI, así que se usa Inter — mismo criterio que en RC-013 con el título de la grilla del alumno.

**La barra de código de la landing no es `Q3CodeInput`.** El tab Alumno usa seis celdas de un carácter (RC-003); el frame de la landing dibuja un input de texto normal con el botón adosado. Son dos componentes distintos por diseño, así que no hay nada que reusar ni promover a `global/` — y de paso evita el cruce entre módulos.

**El código viaja en la URL, no en estado de navegación.** `/acceso?tipo=alumno&codigo=XXX` es el contrato que RC-011 ya definió para los enlaces compartidos (HU-09 Escenario 3) y que `Q5StudentAccessFlow` ya sabe leer: la landing no necesita nada nuevo del lado de `access`, y el enlace resultante se puede copiar y pegar.

### Decisiones resueltas (Diego Canelo, 2026-08-09)

**D1 · La landing va en `home`, con `homePublicRoutes` aparte — APROBADO.**
`/` se registra fuera de `Q5ProtectedRoute`; las tres rutas privadas siguen adentro en `homeRoutes`. Se descarta el módulo `landing` nuevo: `docs/tech-document.md` §RC-007 ya asigna la landing a `home`.

**D2 · `PaHealth` se mueve a `/health` — APROBADO.**
No se elimina ni se esconde detrás de `import.meta.env.DEV`: sirve en desarrollo para diagnosticar los emuladores y, fuera de `/`, no le estorba a nadie. El módulo `health` sigue existiendo tal cual.

**D3 · Doble validación del código — APROBADO.**
La landing valida para poder mostrar el error del Escenario 3, y `/acceso` vuelve a validar porque además necesita la sala, la sesión anónima y el chequeo de respuesta previa. Son dos lecturas de un documento chico con un segundo de diferencia; la experiencia lo justifica.

**D4 · Código de sala cerrada — APROBADO.**
La landing no mira `status`: redirige con el código y el flujo del alumno muestra "Esta sala ya no acepta respuestas". La regla queda en un solo lugar (RC-003), sin duplicar lógica. Incorporado a §4, §6 y §9.

### Notas de implementación (2026-08-09)

Implementado por el agente `implementer` y verificado de forma independiente: type-check, lint, 294 tests unitarios (59 archivos), 43 E2E y build, todo en verde, más captura propia de la landing y del estado de error contrastada contra el frame `YbL8k`.

- **`Q2LandingFeatureCard` recibe `tone: 'secondary' | 'accent' | 'high'`.** El RC nombraba las tres cards pero no cómo variaba el color del ícono. El prop nombra el token, no el color, así que no entra ningún hex al componente.
- **El input normaliza a mayúsculas al tipear y la navegación usa `room.code`**, el canónico de Firestore, no lo tipeado. Sin eso, escribir `lnd001` generaría un enlace que no coincide con lo que muestran las celdas de `/acceso`.
- **El foco de la barra se marca con `:focus-within` sobre el contenedor**, no con un anillo en el input: un outline interno rompía el marco de 460×56 del frame. El estado de error gana sobre el de foco.
- **`route-guard.spec.ts` no necesitó cambios** pese a que hace `goto('/')`: la landing es pública y no redirige sin sesión, así que sus tres escenarios siguen valiendo.
- **Se agregaron dos tests no pedidos explícitamente** (`landing-code.schema.test.ts` y `use-landing-code-mutation.test.tsx`), por consistencia con el resto de `home/core`, donde todos los hooks y schemas tienen test propio.

**Pendientes conocidos, ninguno bloqueante:**
- Desde la landing con un código válido, el visitante llega a `/acceso` con el código precargado pero **tiene que presionar "Ingresar" otra vez**: `Q4RoomCodeForm` no auto-envía un código precargado (comportamiento de RC-011, fuera de alcance acá). Vale la pena que QA lo mire: es un segundo clic sobre una acción que el visitante ya hizo.
- Una caída de red muestra "Código inválido. Revisa con tu ayudante", que es engañoso si el problema es Firestore. Es lo que decidió §4 de este RC, no un descuido.
- La fila de tres cards no colapsa bajo ~700px. Mobile sigue fuera de alcance; la página, la barra y los divisores sí tienen `max-width: 100%` para no desbordar.
- `/health` no está enlazada desde ninguna pantalla: solo se llega por URL directa, que es justo lo que pedía D2.

**Fuera de alcance:** SEO/meta tags y Open Graph, analítica, cualquier sección extra de la landing (precios, contacto, FAQ), mobile (< 1024px, postergado por la HU), el modo oscuro específico de esta pantalla más allá de lo que ya dan los tokens, y tocar el flujo de `/acceso`.
