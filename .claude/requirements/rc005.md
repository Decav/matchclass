## 1. Contexto y Problema

RC-003 dejó `/dashboard` montado como placeholder público (`PaDashboardPlaceholder`) — cualquiera puede navegar ahí sin sesión, aunque el ayudante ya pueda loguearse (RC-003) y registrarse (RC-004). Sin un guard, ninguna ruta privada del ayudante (dashboard, gestión de salas) puede considerarse protegida de verdad.

## 2. Objetivo

Implementar un componente guard (`Q5ProtectedRoute`, patrón ya documentado en `06-auth-integration.md §Capa 7`) que envuelva las rutas privadas del ayudante — hoy solo `/dashboard`, y cualquier ruta bajo `/salas/*` que agregue RC-004 más adelante — redirigiendo a `/acceso` si no hay sesión, y mostrando un spinner mientras Firebase restaura la sesión (sin flash de `/acceso`).

## 5. Puertos (Interfaces)

No se agregan repositorios ni puertos nuevos. Se consume lo que ya expone RC-003:

- `useAuthStore` (`src/global/store/auth.store.ts`) — `status: AuthStatus`, ya sincronizado por `AuthProvider`/`onAuthStateChanged` desde que la app monta.

## 6. Componente

- **Q5ProtectedRoute** (`src/global/components/q5-protected-route/`)
  - Sin props obligatorias (usa `useAuthStore` internamente); admite `redirectTo?: string` (default `/acceso`) para no hardcodear la ruta pública si cambia más adelante
  - Layout route de React Router: renderiza `<Outlet />` cuando `status === 'authenticated'`
  - Si `status` es `'idle'` o `'loading'` → `<Q1LoadingSpinner size="lg" label="Verificando sesión..." />` centrado con el logo (ya existe el patrón en `PaDashboardPlaceholder`/`AccessPage` — ver Notas)
  - Si `status === 'unauthenticated'` → `<Navigate to={redirectTo} replace />`

### Comportamiento
1. Al montar cualquier ruta hija, lee `status` de `useAuthStore` (ya actualizado por `AuthProvider`, que corre antes que el router — RC-003 §Capa 5)
2. `idle`/`loading` → spinner, nunca `/acceso` ni el contenido protegido (Escenario 4)
3. `authenticated` → `<Outlet />` (Escenario 1)
4. `unauthenticated` → `<Navigate to="/acceso" replace />` (Escenario 2); `replace` evita volver con "atrás" (Escenario 2, 5)
5. Rutas públicas (`/`, `/acceso`, `/registro`) no pasan por este componente — no se tocan sus rutas actuales

## 10. Notas

**Numeración fuera de orden respecto a `docs/tech-document.md`.** El tech-document asigna "RC-005" a "Respuesta del alumno" (módulo `scheduling`). Este RC toma el número 5 solo por ser el siguiente archivo secuencial en `.claude/requirements/` — igual que pasó con RC-004 (registro vs. "Gestión de salas" en el tech-document). No renombro RCs anteriores ni el tech-document; lo dejo señalado para que quien lea ambos documentos sepa que los números no coinciden con el plan original.

**Alcance: `/dashboard` ahora, `/salas/*` cuando exista.** HU-03 pide proteger `/dashboard/*` y `/salas/*`, pero ninguna ruta `/salas/*` existe todavía (es RC-004 "Gestión de salas" del tech-document, sin implementar). `Q5ProtectedRoute` se implementa como layout route genérico y reutilizable — RC-004 lo usará para envolver sus propias rutas cuando las cree, sin tocar este componente.

**`/sala/:roomId` (singular, alumno) queda explícitamente fuera del guard.** No confundir con `/salas/*` (plural, gestión del ayudante). `/sala/:roomId` es la pantalla del alumno (RC-003, placeholder hoy, RC-005-scheduling-del-tech-document la completa) a la que se llega con sesión anónima, no con cuenta de ayudante — debe seguir siendo pública. HU-03 no la menciona como ruta a proteger, y no se toca.

**Recuperar contraseña.** Vi que el `.pen` ya tiene frames `Recuperar Contraseña - Email`/`Recuperar Contraseña - Confirmación`, y HU-03 ya lista `/recuperar` como ruta pública futura. No creo esa ruta en este RC — no hay HU que la pida todavía — pero el guard no le impediría existir como pública el día que se implemente.

**Fuera de alcance:** logout (HU-04, el Escenario 5 de HU-03 depende de que exista pero el guard ya queda listo para reaccionar cuando el store pase a `unauthenticated`, sin importar qué lo dispare), CRUD de salas (RC-004 del tech-document), recuperación de contraseña.

## 11. Registro de implementación

**Fecha:** 2026-07-30
**Autor:** Claude

### 11.1. Decisiones tomadas fuera del alcance literal del RC

1. **Sin `requiredRoles` en `Q5ProtectedRoute`.** El patrón documentado en `06-auth-integration.md §Capa 7` incluye una prop `requiredRoles?: string[]` con redirección a `/unauthorized`. El RC (§6) es explícito: la única prop es `redirectTo?: string` (default `/acceso`), sin roles — MatchClass hoy no diferencia roles del ayudante autenticado (`User.roles` existe en el modelo pero no en el uso actual). Se implementó literalmente lo que pide §6, sin la prop de roles del ejemplo genérico del seed, para no agregar superficie no pedida ni un `/unauthorized` inexistente.
2. **`Q5ProtectedRoute` no usa `useLocation`/`state={{ from: location }}` del ejemplo del seed.** El RC no pide preservar la ruta de origen para volver tras el login (`useLoginMutation`, RC-003, ya redirige siempre a `/dashboard` fijo, no lee ningún `state.from`). Agregarlo habría sido código muerto sin nada que lo consuma.
3. **Montaje como layout route con `children: homeRoutes` en vez de anidar manualmente cada ruta de `home`.** El RC sugiere el patrón `{ element: <Q5ProtectedRoute />, children: [...homeRoutes] }` o equivalente; se usó `children: homeRoutes` (sin spread, ya que `homeRoutes` ya es un array de `RouteObject[]`) para que RC futuras que agreguen rutas a `homeRoutes` (o un eventual array `salasRoutes`) queden protegidas por el mismo layout con un cambio de una línea en `app-router.tsx`.
4. **Comentarios actualizados en `pa-dashboard-placeholder.tsx` y `app-router.tsx`** para dejar de decir "sin guard todavía" — ya no aplica desde este RC. No se tocó ninguna lógica de `PaDashboardPlaceholder`, solo la documentación inline que quedaba desactualizada.

### 11.3. Pendientes / riesgos

- **"Validado por QA"** (Criterios de Aceptación, último ítem): no puede darlo por cerrado un agente. Los 5 escenarios de `docs/hu-03-guard-rutas.md` tienen cobertura automatizada (unit + E2E contra emuladores reales) y verificación visual manual, pero falta el visto bueno humano que el propio RC pide literalmente.
- **Escenario 5 (logout redirige a `/acceso`) no tiene test propio en este RC** — depende de HU-04 (logout), explícitamente fuera de alcance. `Q5ProtectedRoute` ya reacciona correctamente a cualquier transición de `status` a `unauthenticated` (lo prueba el test de componente con `unauthenticated` directo), así que no requiere cambios cuando HU-04 se implemente, pero el escenario end-to-end completo solo podrá probarse una vez exista el botón de logout.
- **`/registro` sigue sin redirigir a un ayudante ya autenticado que navegue ahí manualmente** (pendiente heredado de RC-004 §11.3) — no es parte del alcance de este RC (que protege `/dashboard` contra usuarios sin sesión, no rutas públicas contra usuarios con sesión) y no se tocó.
- **`/salas/*` queda sin crear** — cuando RC-004-del-tech-document ("Gestión de salas") agregue esas rutas, deben montarse como hijas de `Q5ProtectedRoute` (o de un layout route hermano que también lo use) para heredar el guard; este RC no las agrega ni las asume.
