## 1. Contexto y Problema

MatchClass está completo de punta a punta —landing, acceso, dashboard, grilla del alumno, resultados— y no está publicado en ningún lado. El repo tampoco sabe desplegarse: **`firebase.json` no tiene bloque `hosting`**, solo `firestore` y `emulators`. Todo lo que existe hoy corre contra emuladores locales.

## 2. Objetivo

Dejar el repo en condiciones de publicar en `matchclass.web.app`: configuración de Hosting con rewrites de SPA, entorno de producción, reglas de Firestore desplegables, y una lista de verificación de lo que hay que confirmar en la consola de Firebase.

## 3. Entidades y Value Objects

Ninguna. Este RC no toca dominio.

## 4. Errores de Dominio

No aplica. Lo que sí importa es un comportamiento de arranque que ya existe y conviene tener presente al configurar producción:

`readFirebaseEnv()` (`src/library/firebase/env.ts`) **lanza** si falta `VITE_FIREBASE_API_KEY`, `AUTH_DOMAIN`, `PROJECT_ID` o `APP_ID`. Es deliberado —mejor no arrancar que apuntar a ninguna parte— pero significa que un `.env.production` incompleto se manifiesta como **pantalla en blanco**, no como un error suave. Es la razón por la que el Escenario 5 no es cosmético.

`VITE_FIREBASE_USE_EMULATORS` se evalúa como `=== 'true'`, así que si la variable falta, el default es producción. Seguro por diseño.

## 5. Puertos (Interfaces)

- **`firebase.json`** — bloque `hosting` nuevo:
  - `public: "dist"`
  - `rewrites`: `[{ "source": "**", "destination": "/index.html" }]` — es lo único que hace pasar el Escenario 6 (React Router es client-side; sin esto, `/acceso` devuelve 404)
  - `ignore`: `firebase.json`, dotfiles, `node_modules`
  - `headers`: `no-cache` con `source: "**"` para el HTML, y cache larga para `/assets/**` (Vite ya los sirve con hash en el nombre), declarada **después** del catch-all para que gane sobre él

    > **Corregido el 2026-08-10, contra el sitio ya publicado.** Este RC especificaba `source: "/index.html"`, y así se implementó y desplegó. No funciona: Hosting matchea los headers contra **la URL pedida**, no contra el archivo que sirve. `/index.html` recibía el `no-cache`, pero `/`, `/acceso` y todas las rutas de la SPA caían en el default de `max-age=3600` — o sea que la regla no alcanzaba a ningún visitante real y, tras cada deploy, quien ya había entrado seguía viendo la versión anterior hasta una hora. El `source` correcto es `**`. Verificado con `curl` antes y después del redeploy, incluido que los assets conserven `immutable`.

- **`.env.production`** — las seis `VITE_FIREBASE_*` del proyecto real, `VITE_FIREBASE_USE_EMULATORS=false` y `VITE_APP_ENV=production`. Vite lo toma solo en `npm run build` (modo `production`), sin tocar `.env.local`

- **`.env.example`** — se documenta la existencia de `.env.production` y qué lo distingue de `.env.local`

- **`src/library/firebase/firebase-app.ts`** — la base de producción es **nombrada** (D1 confirmada), así que el id se elige según el entorno:

  ```ts
  const FIRESTORE_DATABASE_ID = 'matchclass-db';

  // Los emuladores sirven la base `(default)`; el proyecto real usa una
  // base nombrada. Sin esta distinción, producción apunta a una base vacía.
  export const db: Firestore = env.useEmulators
    ? getFirestore(firebaseApp)
    : getFirestore(firebaseApp, FIRESTORE_DATABASE_ID);
  ```

- **`firebase.json`** — al bloque `firestore` se le agrega `"database": "matchclass-db"`, o `deploy --only firestore:rules` publicaría las reglas en la base equivocada

- **`firestore.rules`** — sin cambios de contenido: las reglas ya están escritas y probadas contra el emulador. Este RC solo las despliega

- **`README.md` o `docs/`** — el procedimiento de despliegue y la checklist de consola, para que no viva en la cabeza de una persona

**No se toca `src/` fuera de lo de D1**, ni las Cloud Functions de RC-017 (van en su propio deploy).

## 6. Use Cases

No hay use cases de negocio. El procedimiento operativo, que es lo que este RC deja escrito y verificable:

### DeployProduccion
1. `npm run type-check`, `npm run lint`, `npx vitest run` y `npx playwright test` en verde (Escenario 1)

**Los pasos 3 y 4 los ejecuta Diego, no la IA** (`CLAUDE.md` §Firebase): son acciones irreversibles sobre el único proyecto real que existe.

- **Dominios autorizados** de Auth: `matchclass.web.app` y `matchclass.firebaseapp.com`
- Base de datos de Firestore creada y con su id confirmado (D1)

- [ ] Un test valida que `firebase.json` tiene `hosting.public === 'dist'`, un rewrite `**` → `/index.html` y `firestore.database === 'matchclass-db'` (Escenarios 3 y 6, sin depender de recordar la config)

- [ ] **`npx playwright test` sigue en verde tras agregar `database` a `firebase.json`** — los e2e corren contra la base `(default)` del emulador y esa clave no debe alterarlos

### Verificación manual en producción (no automatizable desde acá)
- [ ] `matchclass.web.app/` carga la landing (Escenario 2)
- [ ] `matchclass.web.app/acceso` carga directo, sin 404 — prueba real del rewrite (Escenarios 2 y 6)

- [ ] **Una sala creada en producción aparece efectivamente en la consola de Firestore, dentro de `matchclass-db`** — la prueba de que la app quedó apuntando a la base nombrada y no a una `(default)` vacía (D1)

## 10. Notas

**Los enlaces de sala ya son agnósticos del dominio.** `buildAlumnoAccessLink` usa `window.location.origin`, así que en producción genera `matchclass.web.app/...` sin ningún cambio. El ítem del DoD se cumple por diseño: **no hardcodear el dominio** para "arreglarlo".

**El bundle es un solo chunk de 1.14 MB (341 kB gzip)** y el build ya emite el aviso de tamaño. Diego lo dio por aceptable para la v1: el code splitting por ruta queda para después, como RC propio.

**Lo que este RC no puede verificar solo.** Los Escenarios 2, 3, 4 y 6 se comprueban contra el sitio publicado; hasta que exista el deploy, quedan como checklist manual. Es la naturaleza de la HU, no una carencia del RC.

### Decisiones resueltas (Diego Canelo, 2026-08-09)

**D1 · La base es nombrada: `matchclass-db`, no `(default)` — CONFIRMADO.**
La creó Diego en la consola con ese nombre. Era el punto que decidía si el despliegue publicaba una app funcionando o una vacía: `getFirestore(firebaseApp)` siempre resuelve a `(default)`, así que hoy producción apuntaría a una base sin datos, cargando bien y sin encontrar ninguna sala. Se resuelve en tres piezas, todas en §5:
- `firebase-app.ts` elige el id según el entorno: `(default)` con emuladores, `matchclass-db` contra el proyecto real
- `firebase.json` declara `"database": "matchclass-db"` para que las reglas se publiquen donde corresponde
- **Emuladores y e2e siguen con `(default)`, sin cambios**

**D2 · `.env.production` se commitea — APROBADO.**
Las claves `VITE_FIREBASE_*` son públicas por diseño y ya está documentado en `CLAUDE.md` y en `.env.example`. Commitearlo hace el build reproducible y evita el clásico "me falta una variable" en el deploy. Que un `.env.production` incompleto termine en pantalla en blanco es el comportamiento correcto de `readFirebaseEnv` y no se toca.

**D3 · Sentry queda fuera de alcance — APROBADO.**
`VITE_SENTRY_DSN` está tipada y documentada, pero ningún archivo la lee y Sentry no es dependencia: configurar el DSN no haría nada. Diego lo sacó de la HU-16. Integrarlo es un RC propio — inicialización, filtrado de PII y source maps del build son una feature completa, no una variable de entorno.

**D4 · El despliegue lo ejecuta Diego — CONFIRMADO.**
`firebase deploy` no va en el RC ni lo corre la IA. Con un solo proyecto y sin staging, cada deploy pisa producción directamente. El RC deja todo configurado y verificado localmente; el comando es del usuario.

**D5 · El criterio extra del test de `firebase.json` — APROBADO.**
Se valida por test el rewrite de SPA, `public: "dist"` y el id de base, para que el Escenario 6 y la D1 no dependan de que alguien se acuerde de mirar la configuración.

### Notas de implementación (2026-08-10)

Implementado por el agente `implementer` y verificado de forma independiente: type-check, lint, **313 tests unitarios (62 archivos)**, **43 E2E** y build, todo en verde.

- **El test de la base se validó por mutación.** La aserción que hace el trabajo no es `toHaveBeenCalledWith` sino la cantidad de argumentos: `getFirestore(app, 'x')` también satisface `toHaveBeenCalledWith(app)`, así que el caso de emuladores habría pasado con el ternario roto. Se comprobó reemplazando el ternario por `getFirestore(firebaseApp)`: el test falla.
- **`.env.production` estaba explícitamente en `.gitignore`.** Versionarlo (D2) exigió sacarlo de ahí. Es la línea que un lector desprevenido va a intentar "arreglar": las claves web son públicas por diseño y viajan en el bundle.
- **La documentación quedó en `docs/despliegue.md`** y no en un `README.md` nuevo: el repo no tiene README en la raíz, y crearlo solo para el deploy obligaba a escribir además la presentación del proyecto.
- **Los e2e siguen verdes tras agregar `firestore.database`**: el dev server usa `.env.local` con `USE_EMULATORS=true`, así que el ternario cae en la rama `(default)`.

**Pendiente de coordinación entre ramas:** RC-017 y RC-019 editaron `firebase.json` por separado —`functions` + emulador 5001 uno, `hosting` + `firestore.database` el otro— y ninguna de las dos ve el bloque de la otra. Al mergear la segunda hay que confirmar que el archivo queda con las cuatro claves (`firestore` con `database`, `functions`, `hosting`, `emulators` con el puerto de functions). El test de `firebase.json` de este RC no lo detectaría: solo valida lo suyo.

**Fuera de alcance:** dominio propio y certificados, CI/CD (GitHub Actions), **Sentry** (D3, RC propio), **code splitting del bundle** (RC propio), previews de Hosting por PR, y el despliegue de las Cloud Functions de RC-017 (que tiene su propio deploy y su propio dry-run).
