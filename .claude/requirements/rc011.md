## 1. Contexto y Problema

Copiar el código de la sala **ya funciona** desde RC-008 (card del dashboard) y RC-009 (pantalla de confirmación) — ambos ya usan `navigator.clipboard.writeText` con confirmación visual. Lo que falta de HU-09: copiar el **enlace completo** (con el código precargado para el alumno) y un **fallback** cuando el navegador no soporta la Clipboard API. Sin esto, compartir por WhatsApp/Discord obliga al alumno a escribir el código a mano en vez de solo abrir un link.

## 2. Objetivo

Agregar "Copiar enlace" (código + query param `codigo` para precargar el tab Alumno) en la card del dashboard y en la confirmación de creación, con fallback de selección manual cuando no exista `navigator.clipboard`, y hacer que `/acceso?tipo=alumno&codigo=X` realmente precargue ese código en el formulario.

---

## 3. Entidades y Value Objects

No aplica. No hay entidades ni VOs nuevos — es una utilidad de construcción de URL y un helper de portapapeles con fallback.

## 4. Errores de Dominio

No aplica. Copiar al portapapeles no es una operación de dominio que pueda fallar de forma que la HU pida mostrar un mensaje de error — cuando `navigator.clipboard` no existe, el comportamiento esperado (Escenario 4) es el fallback de selección, no un error.

## 5. Puertos (Interfaces)

- **`copyOrSelect`** (`src/global/utils/copy-to-clipboard.ts`, nuevo, sin conocer dominios):
  - `copyToClipboard(text: string): Promise<boolean>` — usa `navigator.clipboard.writeText` si existe; devuelve `false` si no existe o si falla (no lanza)
  - `selectElementText(el: HTMLElement): void` — fallback del Escenario 4: selecciona el contenido del elemento (Selection API) para que el usuario lo copie con `Ctrl+C`/`Cmd+C` manualmente. No intenta `document.execCommand` (deprecado) — la HU pide literalmente "se muestra el código seleccionado", no una copia programática alternativa

- **`buildAlumnoAccessLink`** (`src/resources/utils/build-alumno-access-link.ts`, nuevo, mismo criterio que `generateShortCode` de RC-009 — pura, sin SDK):
  - `(code: string, origin?: string) => string` — devuelve `${origin ?? window.location.origin}/acceso?tipo=alumno&codigo=${code}`. Parámetro `origin` opcional solo para poder testear sin `window` real

## 6. Comportamiento

### Copiar código (Escenarios 1, 2 — ya implementado, sin cambios)
`Q3RoomCard` (RC-008) y `Q4RoomCreatedConfirmation` (RC-009) ya copian el código con `navigator.clipboard.writeText` y feedback visual (ícono cambia a check, o label "¡Copiado!"). Este RC no los modifica — solo verifica que sigan funcionando.

### Copiar enlace (Escenario 3 — nuevo)
1. Se agrega un botón/ícono "Copiar enlace" en `Q3RoomCard` (junto al botón "Copiar" existente) y en `Q4RoomCreatedConfirmation` (junto al código)
2. Al presionarlo: `copyToClipboard(buildAlumnoAccessLink(room.code))`
3. Mismo patrón de confirmación visual ya usado para "Copiar" (ícono → check, ~1.5s)
4. `/acceso` lee el query param `codigo` (además del ya existente `tipo`) y, si el tab activo es Alumno, precarga ese valor en `Q4RoomCodeForm` como valor inicial del código (normalizado a mayúsculas, igual que la validación manual) — el alumno llega, ve el código ya escrito, y solo tiene que confirmar

### Fallback sin Clipboard API (Escenario 4 — nuevo)
1. Antes de copiar (código o enlace), se verifica si `navigator.clipboard.writeText` existe
2. Si no existe: en vez de copiar, se selecciona visualmente el texto del código (`selectElementText` sobre el elemento donde ya se muestra el código en pantalla) para que el usuario lo copie manualmente — no se muestra el estado "¡Copiado!" (no se copió nada todavía, solo se seleccionó)

## 10. Notas

**La mayor parte de esta HU ya estaba resuelta antes de escribirla.** Escenarios 1 y 2 (copiar solo el código) los implementaron RC-008 y RC-009 sin saber que HU-09 existiría — ambos ya cumplen la letra de esos dos escenarios. Este RC solo agrega lo que faltaba: Escenario 3 (enlace) y Escenario 4 (fallback). No se toca la lógica de copiar-código existente salvo para, si aplica, reusar `copyToClipboard` en vez de la llamada directa a `navigator.clipboard.writeText` que ya tienen (mismo comportamiento, solo evita duplicar el fallback en tres lugares).

**Sin frame de diseño nuevo.** A diferencia de otras HUs de esta épica, HU-09 no trae ni referencia un frame de Pencil específico, y su propio DoD no exige fidelidad visual a un mockup — el botón "Copiar enlace" se agrega con el mismo lenguaje visual ya usado (ícono Lucide `Link`, mismo patrón de confirmación que "Copiar").

**Verificar el portapapeles en Playwright requiere permisos del navegador.** `navigator.clipboard.readText()` en un test E2E necesita `context.grantPermissions(['clipboard-read', 'clipboard-write'])` (Chromium). Si el entorno de CI no lo soporta, una alternativa aceptable es interceptar `navigator.clipboard.writeText` con `page.exposeFunction`/`page.evaluate` para capturar el argumento sin depender de permisos reales.

**Fuera de alcance:** cualquier cambio al flujo de copiar-solo-código ya existente, rediseño visual de las cards o la confirmación, compartir por un canal específico (WhatsApp/Discord/email directo — la HU solo pide que el copiado funcione, no integraciones de compartir nativas tipo `navigator.share`).

**Desviación 1 — se reusó `copyToClipboard` en los botones "Copiar" ya existentes.** El RC (§10) dejaba esto a criterio de quien implementara. Se optó por reusarlo en `Q3RoomCard` y `Q4RoomCreatedConfirmation` en vez de dejar la llamada directa a `navigator.clipboard.writeText`: evita duplicar el fallback de selección (Escenario 4) en tres lugares y hace que "Copiar" (código) también caiga al fallback cuando no hay Clipboard API, no solo "Copiar enlace". Mismo comportamiento observable para el caso feliz (verificado por los tests de regresión de RC-008/RC-009, que siguen pasando sin cambios).

**Desviación 2 — el stub de `navigator.clipboard` en `e2e/dashboard.spec.ts` se pasa como `string`, no como función con closures.** `page.addInitScript`/`page.evaluate` ejecutan en el navegador, pero `e2e/**/*.ts` se type-checkea bajo `tsconfig.node.json` (`npm run type-check` no lo cubre; se verificó con `npx tsc --noEmit -p tsconfig.node.json`), que no incluye la lib `DOM` — referenciar `window`/`navigator` como identificadores TS ahí falla con `TS2304: Cannot find name`. Pasar el script como texto (`page.addInitScript('...')` / `page.evaluate<string | null>('window.__copiedText')`) evita que TS intente resolver esos globals, sin tocar `tsconfig.node.json` (cambio de config compartido, fuera del alcance de este RC). Documentado en el docstring de `stubClipboard`.

**Verificación real (no solo tests):**
- Copiar enlace desde la card del dashboard: `page.evaluate` sobre el stub de `navigator.clipboard.writeText` confirmó que el texto copiado es `${origin}/acceso?tipo=alumno&codigo=DASH01` (E2E `dashboard.spec.ts`)
