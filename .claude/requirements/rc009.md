## 1. Contexto y Problema

RC-008 dejó `/salas/nueva` como placeholder ("en construcción"). El botón "Nueva sala"/"Crear primera sala" del dashboard no lleva a ningún lado funcional — el ayudante no puede crear una sala real todavía, así que tampoco puede empezar a recibir respuestas de sus alumnos.

## 2. Objetivo

Reemplazar el placeholder por el flujo real de dos pasos (formulario → confirmación) que crea el documento en Firestore con un código corto único generado automáticamente, dentro del mismo `Q5AppShell` que ya usa `/dashboard`.

---

## 3. Entidades y Value Objects

No se agrega ninguna entidad de dominio: `Room` ya está definida (RC-003/`tech-document.md §2.1`) y este RC es el primero en **crearla** (antes solo se leía: `findByCode` en RC-003, `listByOwner` en RC-008).

- **CreateRoomFormValues** (VO de formulario, Zod): `name`, `subject`, `section` — los tres obligatorios, sin validación de formato adicional (Escenario 2; la HU no pide nada más que "no vacío")

## 4. Errores de Dominio

| Error | Origen | Mensaje mostrado | Escenario |
|-------|--------|-------------------|-----------|
| RequiredFieldError | validación cliente (Zod) | "Este campo es obligatorio" | 2 |
| NetworkError | falla de red/Firestore al crear el documento | "Error de conexión. Intenta de nuevo" | 7 |
| RoomCodeGenerationError | 3 intentos de generar un código único fallan (colisión) | mismo tratamiento que `NetworkError` en la UI — caso raro (36⁶ combinaciones posibles con códigos de 6 caracteres), sin escenario Gherkin propio, la HU solo pide "reintentar hasta 3 veces antes de fallar" | — |

## 5. Puertos (Interfaces)

- **RoomRepository** (`src/library/repositories/room.repository.ts`) — se agrega:
  - `create(data: Pick<Room, 'name' | 'subject' | 'section' | 'code' | 'createdBy'>): Promise<{ id: string }>` — `addDoc` en `rooms` con `status: 'active'`, `helperBlockedSlots: []`, `createdAt: serverTimestamp()` fijos (no vienen del caller)

- **generateShortCode** (`src/global/utils/generate-short-code.ts`, función pura, sin conocer dominios): `(length?: number) => string` — alfanumérico en mayúsculas. `global` no puede llamarse "room code": es un generador de códigos cortos genérico: el módulo que lo usa (`RoomService`) es quien le da significado de "código de sala"

- **RoomService** (`src/library/services/room.service.ts`, ya existe desde RC-008) — se agrega:
  - `createRoom(uid: string, data: Pick<Room, 'name' | 'subject' | 'section'>): Promise<{ id: string; code: string }>` — genera el código, verifica unicidad con `RoomRepository.findByCode` (ya existe), reintenta hasta 3 veces, y crea el documento

## 6. Use Case

| Use Case | Input | Output | Errores posibles |
|----------|-------|--------|-------------------|
| CreateRoom | name, subject, section | `{ id, code }` → pantalla de confirmación | RequiredFieldError, NetworkError, RoomCodeGenerationError |

### CreateRoom
1. Valida `CreateRoomFormValues` con Zod — bloquea el submit si hay campos vacíos (Escenario 2)
2. `RoomService.createRoom(uid, { name, subject, section })`:
   - Genera un código de 6 caracteres alfanuméricos en mayúsculas (`generateShortCode(6)`)
   - `RoomRepository.findByCode(code)` — si ya existe, repite hasta 3 veces en total
   - Si las 3 generaciones colisionan, lanza `RoomCodeGenerationError`
   - `RoomRepository.create({ name, subject, section, code, createdBy: uid })` → `{ id }`
3. Éxito → la página pasa al paso "confirmación" con `name` y `code` ya conocidos (no hace falta releer Firestore) (Escenario 1)
4. Error (red o generación de código) → mensaje correspondiente, el formulario conserva los valores ingresados, botón vuelve a su estado activo (Escenario 7)
5. "Cancelar" (solo visible en el paso formulario) → navega a `/dashboard` sin crear nada (Escenario 3)
6. Desde la confirmación: "Ir al dashboard" → `/dashboard`, donde la sala nueva ya aparece (Escenario 5, la lista la lee `RoomService.getDashboardRooms` de RC-008, sin cambios); "Configurar mis bloques" → placeholder de HU-08 (Escenario 6, ver Notas)

## 7. Contrato (Firebase)

| Operación | Método Firestore | Input | Output | Errores |
|-----------|-------------------|-------|--------|---------|
| Verificar código único | `getDocs(query(rooms, where('code','==',code), limit(1)))` | code | `Room \| null` | `unavailable` |
| Crear sala | `addDoc(collection(db,'rooms'), {...})` | name, subject, section, code, createdBy, status:'active', helperBlockedSlots:[], createdAt:serverTimestamp() | `{ id }` | `unavailable`, `permission-denied` |

**Longitud del código: 6 caracteres, no un rango variable.** La HU dice "3-6 caracteres alfanuméricos", pero todos los códigos reales en el diseño y en los fixtures de E2E (`EDS101`, `ALG205`, `WEB404`, `DASH01`, etc.) tienen exactamente 6. Se implementa `generateShortCode(6)` fijo — es la opción que ya es consistente con todo lo existente, no una longitud variable sin ningún caso de uso que la pida.

**"Configurar mis bloques" → placeholder de HU-08.** No existe RC para restricciones del ayudante todavía. Se agrega la ruta `/salas/:roomId/bloques` (protegida por `Q5ProtectedRoute`, mismo patrón que el resto de `/salas/*`) con una página mínima "en construcción" — el frame `Configurar Mis Bloques` (`N2rqv`) ya existe en el `.pen` para cuando se escriba esa HU.

**Mismo criterio de módulo que RC-008.** El código de esta RC vive en `src/modules/home/` (reemplaza `PaNewRoomPlaceholder`), no en un módulo `rooms` nuevo — seguir exactamente donde RC-008 dejó los placeholders relacionados (`pa-dashboard`, `pa-room-detail-placeholder`) en vez de fragmentar. El campo "Módulo" de este RC refleja la épica del tech-document, no la carpeta real de código — mismo desfase ya documentado en RC-003/004.

**Fuera de alcance:** configuración de restricciones/bloques (HU-08), gestión/detalle real de una sala existente (`/salas/:roomId` sigue siendo placeholder de RC-008), editar/cerrar/archivar una sala, límite de alumnos (`studentLimit` sigue sin exponerse en el formulario — no lo pide esta HU), cualquier ajuste mobile.
