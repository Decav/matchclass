## 1. Contexto y Problema

MatchClass no tiene todavía ningún mecanismo de acceso implementado. RC-001 dejó el SDK de Firebase inicializado y RC-002 dejó el design system y `Q5AppShell`, pero no existe forma de que un ayudante inicie sesión, ni de que un alumno entre a responder con el código de una sala. La HU-01 actualizada unifica ambos flujos en una sola página (`/acceso`) con dos tabs, y ya no se limita al login: incluye la búsqueda de sala por código, la sesión anónima del alumno y la creación de su respuesta inicial.

## 2. Objetivo

Implementar `/acceso` con sus dos tabs — **Ayudante** (login con email/password contra Firebase Auth + lectura de `users/{uid}`) y **Alumno** (código de 6 caracteres → validación contra `rooms` → sesión anónima → nombre → creación de `rooms/{roomId}/responses/{uid}`) — de modo que ambos actores lleguen a su destino (`/dashboard` o la grilla de la sala) cumpliendo los 16 escenarios de `docs/hu-01-login-ayudante.md`.

## 3. Entidades y Value Objects

- **User** (entidad) — `docs/tech-document.md §2.5`, primera implementación en código:
  - `id: string`, `email: string`, `displayName: string`, `role: 'helper' | 'admin'`, `createdAt: Date | null`

- **Room** (entidad) — `docs/tech-document.md §2.1`. Este RC solo la **lee** (búsqueda por código); CRUD completo queda para RC-004:
  - `id: string`, `code: string` (3-6 chars), `name: string`, `subject: string`, `section: string`, `createdBy: string`, `createdAt: Date`, `status: 'active' | 'closed' | 'archived'`, `helperBlockedSlots: number[]`, `studentLimit?: number`

- **Response** (entidad) — `docs/tech-document.md §2.2`. Este RC la **crea** (nombre + `occupiedBlocks: []`); llenar los bloques es RC-005:
  - `id: string` (= uid anónimo), `roomId: string`, `studentName: string`, `occupiedBlocks: number[]`, `createdByUid: string`, `createdAt: Date | null`, `updatedAt: Date | null`
  - Invariante: `studentName` con al menos 2 caracteres (Escenario 15); `id === createdByUid === uid` de la sesión que escribe

- **AuthStatus** (enum, VO de UI): `'idle' | 'loading' | 'authenticated' | 'unauthenticated'` — distingue "aún no se sabe" de "no hay sesión" para no mostrar un flash de login (Escenario 4)

- **LoginFormValues** (VO, Zod): `email` (formato válido), `password` (no vacío) — Escenario 3

- **RoomCodeFormValues** (VO, Zod): `code` — exactamente 6 caracteres, se normaliza a mayúsculas antes de consultar Firestore (ver `06-auth-integration.md`, Firestore no hace match case-insensitive)

- **StudentNameFormValues** (VO, Zod): `studentName` — mínimo 2 caracteres, trim

## 5. Puertos (Interfaces)

- **AuthRepository** (`src/library/repositories/auth.repository.ts`)
  - `loginWithEmail(email, password): Promise<{ uid: string }>`
  - `ensureAnonymousSession(): Promise<string>` — idempotente, reutiliza sesión anónima existente
  - `subscribeToAuthState(callback: (uid: string | null) => void): () => void`

- **UserRepository** (`src/library/repositories/user.repository.ts`)
  - `getById(uid): Promise<User | null>` — lee `users/{uid}`

- **RoomRepository** (`src/library/repositories/room.repository.ts`)
  - `findByCode(code): Promise<Room | null>` — `where('code', '==', code.toUpperCase())`, `limit(1)`

- **ResponseRepository** (`src/library/repositories/response.repository.ts`)
  - `getMine(roomId, uid): Promise<Response | null>`
  - `submit(roomId, uid, data: Pick<Response, 'studentName' | 'occupiedBlocks'>): Promise<void>`

- **useAuthStore** (`src/global/store/auth.store.ts`) — solo identidad del **ayudante**: `user`, `status`, `setUser`, `clearUser`, `setStatus`. La sesión anónima del alumno no pasa por este store (ver Notas)

## 6. Use Cases

| Use Case | Input | Output | Errores posibles |
|----------|-------|--------|-------------------|
| LoginAyudante | email, password | `User` | InvalidCredentialsError, NetworkError, RequiredFieldError, InvalidEmailFormatError |
| RestoreSession | — (al cargar la app) | `User \| null` | — |
| ValidateRoomCode | code (6 chars) | `{ room: Room; hasExistingResponse: boolean }` | RoomNotFoundError, RoomClosedError, NetworkError |
| SubmitStudentName | roomId, uid, studentName | `void` → redirige a la grilla | StudentNameTooShortError, NetworkError |

### LoginAyudante
1. Valida `LoginFormValues` con Zod (bloquea si hay campos vacíos o email inválido)
2. `AuthRepository.loginWithEmail(email, password)` → `{ uid }`
3. `UserRepository.getById(uid)` → documento `users/{uid}`
4. Combina en un `User` de dominio y actualiza `useAuthStore`
5. Redirige a `/dashboard`

### RestoreSession
1. `AuthRepository.subscribeToAuthState` emite `uid` o `null` al arrancar
2. Si `uid`, `UserRepository.getById(uid)` completa el perfil
3. `useAuthStore.status` pasa a `authenticated` o `unauthenticated`
4. Mientras `status` es `idle`/`loading`, `/acceso` no renderiza tabs (spinner con logo)
5. Si ya `authenticated` al entrar a `/acceso`, redirige a `/dashboard` sin mostrar el formulario

### ValidateRoomCode
1. Bloquea el botón "Ingresar" hasta que las 6 celdas estén completas (Escenario 12)
2. `AuthRepository.ensureAnonymousSession()` → `uid`
3. `RoomRepository.findByCode(code)` → `Room | null`; si `null`, `RoomNotFoundError` (Escenario 10)
4. Si `room.status !== 'active'`, `RoomClosedError` (Escenario 11)
5. `ResponseRepository.getMine(room.id, uid)`:
   - Si existe → `hasExistingResponse: true`, se salta el paso de nombre y redirige directo a la grilla (Escenario 16)
   - Si no existe → muestra la pantalla de nombre con `room.name` (Escenario 9)

### SubmitStudentName
1. Valida `StudentNameFormValues` con Zod (mínimo 2 caracteres, Escenario 15)
2. `ResponseRepository.submit(roomId, uid, { studentName, occupiedBlocks: [] })`
3. Redirige a la grilla de bloques de la sala (Escenario 14)

## 7. Contrato (Firebase)

| Operación | Método/consulta Firebase | Input | Output | Errores |
|-----------|---------------------------|-------|--------|---------|
| Login ayudante | `signInWithEmailAndPassword` | email, password | `FirebaseUser` | `auth/invalid-credential`, `auth/user-not-found`, `auth/network-request-failed` |
| Leer perfil ayudante | `getDoc(doc(db,'users',uid))` | uid | `{displayName, role, email, createdAt}` | doc inexistente (ver Notas) |
| Restaurar sesión ayudante | `onAuthStateChanged` | — | `FirebaseUser \| null` | — |
| Sesión anónima alumno | `signInAnonymously` | — | `FirebaseUser` (anónimo) | `auth/network-request-failed`, `auth/operation-not-allowed` (ver Notas) |
| Buscar sala por código | `getDocs(query(rooms, where('code','==',code), limit(1)))` | code | `Room \| null` | `unavailable` |
| Leer respuesta propia | `getDoc(rooms/{roomId}/responses/{uid})` | roomId, uid | `Response \| null` | — |
| Crear respuesta | `setDoc(rooms/{roomId}/responses/{uid}, {...}, {merge:true})` | roomId, uid, studentName | `void` | `unavailable`, `permission-denied` |

## 10. Notas

**Decisión de alcance (confirmada 2026-07-30):** se implementa un único RC-003 que cubre ambas tabs completas, según lo definido por Diego Canelo — aceptando que cruza los módulos `authentication` (login ayudante), `rooms` (búsqueda de sala por código) y `scheduling` (creación de la respuesta) que `docs/tech-document.md §3` había repartido entre RC-003/RC-004/RC-005 con dependencias en cadena. La regla de capas NDK (`modules → library → global → resources`) no se ve afectada: un mismo módulo de `modules/` puede consumir varios repositorios de `library/`. Lo que se cruza es la planificación de RCs del tech-document, no la arquitectura.

**`Room` y `Response` quedan con contrato mínimo.** Este RC introduce las entidades completas (`docs/tech-document.md §2.1/§2.2`) porque son la fuente de verdad única en `resources`, pero solo ejercita `findByCode`, `getMine` y `submit`. El CRUD de salas (crearlas, cerrarlas, `helperBlockedSlots`) es RC-004; llenar `occupiedBlocks` en la grilla y el matching son RC-005/RC-006. Ningún RC futuro debería redefinir estas entidades, solo sumarles comportamiento.

**Destino "grilla de bloques" — confirmado como placeholder.** Los Escenarios 9, 14 y 16 exigen redirigir a la grilla de la sala, pero esa pantalla es RC-005 y no existe todavía. Este RC crea una ruta placeholder `/sala/:roomId` con un estado mínimo ("grilla en construcción"), igual que RC-002 dejó `Q5AppShell` con navegación vacía para que RC-004/007 la completen. RC-005 reemplaza el contenido de esa ruta.

**Sesión anónima fuera de `useAuthStore` — confirmado.** El store global de auth (`useAuthStore`) representa la identidad del ayudante autenticado con cuenta. La sesión anónima del alumno se maneja como estado local del módulo de acceso (qué paso del flujo — código o nombre — más el `uid`/`roomId` en memoria), sin tocar el store global.

**Testing — se instala en este RC.** El proyecto no tenía Vitest, Testing Library ni Playwright configurados (RC-001 no lo incluyó). Diego Canelo confirmó instalarlo y configurarlo mínimamente como parte de RC-003, ya que `08-testing.md` lo marca obligatorio para flujos de autenticación y este RC es el primero en necesitarlo.

**Anonymous Auth debe habilitarse manualmente.** Firebase Anonymous Auth viene deshabilitado por defecto; hay que activarlo en la consola de cada proyecto (dev/staging/prod) o el SDK devuelve `auth/operation-not-allowed`. Esto depende de que existan los proyectos de Firebase (`CLAUDE.md` los marca como `<POR DEFINIR>`).

**Datos de prueba para el tab Alumno.** Sin RC-004, no hay forma de crear una sala desde la UI. Los tests de componente/E2E de este RC necesitan sembrar `rooms` directamente en el emulador (fixtures), y el propio Diego necesitará una sala de prueba creada manualmente (consola de Firebase o script) para validar el flujo manualmente hasta que exista RC-004.

**Fuera de alcance, aunque compartan página o módulo:** registro de ayudante (HU-02), guard de rutas protegidas (HU-03, ya en `docs/hu-03-guard-rutas.md`), cierre de sesión (HU-04), CRUD de salas (RC-004), grilla de bloques y matching (RC-005/RC-006).

**Discrepancia de ruta sin resolver:** `docs/hu-01-login-ayudante.md` y `docs/design-instrucciones.md` usan `/acceso`; `docs/tech-document.md` y `docs/hu-03-guard-rutas.md` usan `/login`. Este RC usa `/acceso` por ser la especificación más específica y reciente. La ruta de HU-03 debería actualizarse en consecuencia — lo señalo para tu decisión, no lo corrijo por mi cuenta al no estar mencionado en el requerimiento.

**`UserRepository` vs. custom claims.** El seed de arquitectura (`06-auth-integration.md`) ejemplifica roles vía custom claims del ID token; el contrato explícito de HU-01 pide leer `users/{uid}` en Firestore. Se documenta la segunda opción por ser el contrato literal de la HU.

**Documento `users/{uid}` inexistente.** Ningún escenario cubre qué pasa si `auth.currentUser` existe pero falta el documento de Firestore. No se define comportamiento en este RC. **Resuelto durante la implementación** (ver §11.1): se trata como "sin sesión de ayudante" (`clearUser`), nunca como error ni como sesión colgada en `Loading`.

## 11. Registro de implementación

**Fecha:** 2026-07-30
**Autor:** Claude

### 11.1. Decisiones tomadas fuera del alcance literal del RC

1. **Placeholder `/dashboard` nuevo, no contemplado explícitamente en el RC.** El RC pide que `LoginAyudante` redirija a `/dashboard` y que el E2E lo verifique, pero `/dashboard` es RC-007 y el router (RC-001/002) no tenía ninguna ruta con ese path — sin ella, `navigate('/dashboard')` caía en el catch-all (`Navigate to="/"`) y el Escenario 1/4 quedaban imposibles de verificar de punta a punta. Se agregó `src/modules/home/components/pa-dashboard-placeholder/` + `src/modules/home/routes/home.routes.tsx`, montado en `app-router.tsx`, con el mismo criterio que el propio RC ya usa para `/sala/:roomId` ("mismo patrón que RC-002 dejó `Q5AppShell` con navegación vacía"). Sin guard — es pública, igual que `/sala/:roomId` — hasta que HU-03 la proteja.

2. **`Documento users/{uid}` inexistente → tratado como "sin sesión de ayudante".** El RC (§10) deja este caso sin definir. `AuthProvider` lo resuelve así: si `onAuthStateChanged` emite un `uid` pero `UserRepository.getById(uid)` devuelve `null` (o falla), se llama `clearUser()` (→ `Unauthenticated`) en vez de dejar el store colgado en `Loading` o lanzar. Cubre tanto el caso "ayudante sin perfil creado" como, indirectamente, una sesión anónima de alumno que por algún motivo pasara por este listener.

3. **`useLoginMutation` actualiza `useAuthStore` explícitamente, no solo vía `AuthProvider`.** El patrón genérico del seed (`04-patterns.md`/`06-auth-integration.md`) comenta "no se llama a `setUser` aquí: `onAuthStateChanged` ya actualiza el store". Pero el use case `LoginAyudante` del RC (§6) especifica explícitamente los pasos "3. lee `users/{uid}`" y "4. combina en un `User` y actualiza `useAuthStore`" *dentro* del propio use case. Se implementó tal cual pide el RC: la mutation llama a `UserRepository.getById` y a `setUser` ella misma, además de que `AuthProvider` lo vuelve a hacer un instante después vía `onAuthStateChanged` (que sigue siendo la fuente de verdad canónica). Es una llamada duplicada a `UserRepository.getById` en el camino feliz, aceptada a cambio de cumplir el contrato literal del RC y evitar cualquier parpadeo entre el `mutate` exitoso y el evento async del listener.

4. **`toDateOrNull` (`src/library/firebase/firestore-mappers.ts`) en vez del `data.createdAt?.toDate?.() ?? null` literal del seed.** El encadenamiento opcional que muestra `06-auth-integration.md` dispara `@typescript-eslint/no-unsafe-call`/`no-unsafe-member-access` bajo `tseslint.configs.recommendedTypeChecked` (activo en este proyecto, no en el seed). Se extrajo un helper que hace `instanceof Timestamp` antes de llamar `.toDate()` — mismo resultado, sin `any` de por medio. Se usa en los tres repositorios nuevos (`user`, `room`, `response`).

5. **`Q2InputField` (RC-002) ampliado con `endAdornment?: ReactNode` y `error`/`hint` tipados `| undefined` explícito.** No existía ningún consumidor de este componente antes de este RC. El toggle de visibilidad de contraseña (pedido por HU-01 "Comportamiento Visual") necesitaba un slot al final del input; y pasar `error={fieldState.error?.message}` de React Hook Form con `exactOptionalPropertyTypes: true` requiere que el tipo acepte `undefined` explícito, no solo la ausencia de la prop. Cambio aditivo, no rompe el uso existente.

6. **`Q2Alert` nuevo en `src/global/components/`.** Corresponde al componente "Error Alert" del frame `Auth Components` del `.pen`. Es genérico (recibe `message`, sin conocer dominio), reutilizable por cualquier formulario futuro — se puso en `global`, no en el módulo `access`, seteando el mismo precedente que `Q2Forbidden`.

7. **Clases utilitarias nuevas en `theme.css`:** `.mc-access-*` (card/tabs/logo de `/acceso`), `.mc-code-cell(--error)`, `.mc-room-badge`, `.mc-alert(-danger)`. Ninguna estaba en el set de RC-002; se agregaron porque los componentes de este RC las consumen, siguiendo el mismo principio que dejó RC-002 documentado ("clases MatchClass para patrones recurrentes"). Todos los valores mapean 1:1 a los tokens `--mc-*` ya existentes — no se inventó ningún color nuevo (se verificaron contra las variables del `.pen`: `bg-page`→`--mc-surface`, `bg-card`→`--mc-card`, `bg-elevated`→`--mc-surface-alt`, `border-default`→`--mc-border`, etc.).

8. **Testing instalado y configurado end-to-end (confirmado por Diego, RC §10).** Se agregaron `vitest`, `@vitest/coverage-v8`, `@testing-library/react`, `@testing-library/jest-dom`, `@testing-library/user-event`, `jsdom`, `@playwright/test` como devDependencies; `test` en `vite.config.ts`; `src/test/setup.ts`; scripts `test`/`test:watch`/`test:coverage`/`e2e` en `package.json`; `playwright.config.ts`. Además se agregaron `firebase-tools` y `firebase-admin` como devDependencies — no estaban en el proyecto (RC-001 asumía `firebase` en el PATH) — porque el E2E de autenticación (obligatorio según `08-testing.md`) necesita levantar los emuladores y sembrar datos (`e2e/global-setup.ts` usa `firebase-admin` conectado a los emuladores vía `FIRESTORE_EMULATOR_HOST`/`FIREBASE_AUTH_EMULATOR_HOST`). Los 5 E2E se corrieron y pasaron contra emuladores reales (Auth + Firestore) en esta misma sesión, dos veces, con datos sembrados frescos cada vez.

9. **Excepción de lint para tests: `no-restricted-imports` desactivado en `**/*.test.{ts,tsx}`.** Los tests de componente simulan errores de Firebase con `new FirebaseError('auth/invalid-credential', ...)` (patrón explícito de `08-testing.md`, "Simular un error de Firebase en un test"), lo que requiere importar `firebase/app` fuera de `library/`. Se acotó la excepción a archivos de test — el código de producción sigue sin poder importar `firebase/*` fuera de `library/`.

10. **Módulo `scheduling` creado ahora, no en RC-005, solo para el placeholder de `/sala/:roomId`.** El RC ya lo pedía como placeholder (§10); se le dio su propio módulo (`src/modules/scheduling/`) en vez de meterlo dentro de `access`, alineado con la asignación de módulos de `docs/tech-document.md §3` (RC-005 = módulo `scheduling`). RC-005 reemplaza el contenido de `PaRoomPlaceholder`, no la estructura del módulo.

### 11.3. Pendientes / riesgos

- **"Validado por QA"** (DoD, último ítem): no puede darlo por cerrado un agente. Los 16 escenarios de `docs/hu-01-login-ayudante.md` tienen cobertura automatizada (unit + component + E2E contra emuladores reales), pero falta el visto bueno humano que el propio RC pide literalmente.
- **Anonymous Auth en los proyectos reales (dev/staging/prod).** Sigue sin poder verificarse: `CLAUDE.md` marca esos proyectos como `<POR DEFINIR>`. Los E2E y el flujo manual se probaron contra el emulador local, donde Anonymous Auth ya viene habilitado por defecto.
- **Bundle >500kB** (mismo warning ya señalado en RC-002): no se abordó code-splitting en este RC: no formaba parte del alcance y el bundle no creció por una razón atribuible a `/acceso` (Firebase + PrimeReact ya pesaban eso desde RC-001/002).
- **`RC-004` (creación de salas)** sigue sin existir: para que Diego pruebe el tab Alumno manualmente contra el proyecto Firebase real (no el emulador) sigue haciendo falta sembrar una sala a mano en la consola, tal como ya anticipaba la Nota "Datos de prueba para el tab Alumno" del RC.
- **`e2e/global-setup.ts` es idempotente pero no limpia entre corridas.** Reutiliza el usuario/salas si ya existen (`getUserByEmail` / `where('code', ...)`) en vez de recrearlos — corre bien repetidas veces contra el mismo emulador, pero no borra datos de corridas de test previas. Suficiente para este RC; si el volumen de fixtures crece en RC-004/005, conviene mover a `--import`/`--export-on-exit` con una carpeta `e2e/fixtures/` versionada (el `.gitignore` ya reserva `e2e/fixtures/**/*.local` para esto).

### 11.4. Correcciones post-implementación (2026-07-30, tras uso manual de Diego)

Diego probó `/acceso` manualmente con `npm run dev` y reportó dos problemas reales que la verificación de §11.2 no detectó correctamente (la comparación visual contra el `.pen` que ese punto reporta como "coinciden" **no era precisa** — se corrigió en el momento):

1. **Botón e inputs sin estilo alguno (bug real, no solo percepción).** Causa raíz: `PrimeReactProvider` nunca recibió un preset ni un theme clásico (`app-providers.tsx` solo pasaba `{ ripple: true }`), y esta versión de PrimeReact (`primereact@10.9.8`, cuyo `api.d.ts` expone `unstyled`/`changeTheme`, no `theme.preset`) no aplica ningún CSS a `.p-button`/`.p-inputtext` sin uno de los dos. `primereact/resources/primereact.min.css` (importado en `main.tsx`) está deprecado y vacío en esta versión — no aportaba nada. Se probó primero instalar `@primeuix/themes` + `definePreset(Aura, ...)` tal como sugiere (con el nombre de paquete equivocado, `@primereact/themes`, que no existe en npm) `12-design-system.md §6.1`, pero esa API tampoco aplica a esta versión instalada (mismo problema: `theme` no es una prop reconocida de `APIOptions`). Se revirtió esa dependencia y se optó por la vía que RC-002 ya había dejado construida y sin usar: `Q1Button` ahora renderiza un `<button>` nativo con `.mc-btn`/`.mc-btn-{variant}` (sin envolver `Button` de PrimeReact), y se agregó `.mc-form-input` a `theme.css` para que `Q2InputField` tenga borde/fondo/foco/estado inválido sin depender de `.p-inputtext`. `Q3CodeInput` no se vio afectado — ya usaba su propia clase `.mc-code-cell`.
2. **Color del botón primario no coincidía con el diseño.** `.mc-btn-primary` usaba `--mc-brand-gradient` (navy→índigo); el frame real `Primary Button` del `.pen` es navy sólido (`--mc-brand-primary`). Se cambió el fondo a sólido; `--mc-brand-gradient` queda disponible para otros usos pero deja de ser el default del botón primario en toda la app (afecta cualquier componente que use `Q1Button`/`.mc-btn-primary`, no solo `/acceso`).
3. **Copy en voseo corregido a español neutro** (preferencia explícita de Diego, ver memoria `feedback-no-voseo-copy`): "Ingresá un email válido" → "Ingresa un email válido" (`login.schema.ts`), "¿No tenés cuenta?" → "¿No tienes cuenta?" (`q4-login-form.tsx`), "Revisá con tu ayudante" → "Revisa con tu ayudante" (`q4-room-code-form.tsx`), "Intentá de nuevo" → "Intenta de nuevo" (`use-firebase-error.ts`). Tests actualizados en el mismo cambio (`login.schema.test.ts`, `q4-login-form.test.tsx`, `q4-room-code-form.test.tsx`).
4. **`net::ERR_CONNECTION_REFUSED` al iniciar sesión — no era un bug de código.** Los emuladores de Firebase (`npm run emulators`) no estaban corriendo; `VITE_FIREBASE_USE_EMULATORS=true` hace que el SDK intente `localhost:9099` sin fallback. Se inició el emulador manualmente para verificar; queda como recordatorio operativo para Diego: `npm run dev` y `npm run emulators` deben correr en paralelo durante desarrollo local (no se agregó ninguna detección/mensaje especial para este caso, fuera del alcance de esta corrección).

Reverificado después de estos cuatro cambios: `type-check`/`lint`/`build`/`vitest run` (61/61) sin errores, y captura visual (`npx playwright screenshot`) contra el emulador real confirmando que el botón/inputs ahora coinciden con `matchclass_design.pen` (frame `Primary Button` y `Acceso Desktop - Ayudante`), incluyendo el flujo de error de credenciales inválidas probado de punta a punta contra el emulador (Escenario 2). Playwright E2E no se re-corrió después de este cambio (queda pendiente antes de dar por cerrado del todo el DoD).
